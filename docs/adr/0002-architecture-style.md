# ADR-0002: 架构风格——模块化单体 + 独立服务 + 异步解耦

## Status

Accepted

## Context

JobPilot AI 需要确定系统整体形态。曾存在一份 V1.0 设计采用「Gateway + 5 个 C++ 微服务 + 自研 RPC + 服务注册中心」，后经评审认定为过度设计。本 ADR 记录最终裁决，作为后续所有设计的唯一依据。

约束：

- 单人开发，3-6 个月交付
- 必须可运行、可演示、可部署
- 面向 C++ 后端岗位，面试价值优先
- AI（LLM 调用）与爬虫是天然异步、慢、需重试的工作负载

## Decision Drivers

- **业务规模**：单用户 + 自用数据，业务并发需求低，多个同构 C++ 服务进程无实际收益
- **异构服务**：AI / 爬虫用 Python，与 C++ 业务本质不同，天然应独立
- **异步边界**：LLM 秒级延迟、爬虫 IO 密集，适合用消息队列解耦，而不是同步 RPC
- **开发成本**：自研 RPC 框架 + 注册中心 + 服务拆分 = 数周无展示价值的工作量

## Considered Options

### 选项 1：全微服务 + 自研 RPC（V1.0 方案）

- **Pros**：形态像大厂微服务；模块完全隔离
- **Cons**：单人一年工作量；自研 RPC/注册中心面试价值低；每个服务都要重复基础设施；事务跨库；部署复杂度爆炸

### 选项 2：纯模块化单体（C++ 单进程 + 直接函数调用）

- **Pros**：开发最快；部署最简单；事务好写
- **Cons**：AI / 爬虫的异步解耦没有承载点；前后端与 AI 的边界不清晰

### 选项 3：模块化单体 + 独立 Python 服务 + 消息队列（本方案）

- **Pros**：业务在一个进程内内聚；AI/爬虫因异构语言天然独立；MQ 只服务于真正需要解耦的异步场景；演进路径清晰
- **Cons**：需要引入消息队列基础设施；业务模块若未来膨胀需二次拆分

## Decision

采用**选项 3**：

1. **C++ Backend = 模块化单体**：一个 `jobpilot_server` 进程，内含 user / resume / job / application / ai_task 五个业务模块，通过进程内函数调用协作，共享一个 MySQL 连接池与 Redis。
2. **Gateway 接入层**：Nginx 承担 API 网关角色（路由、鉴权前置校验、限流、HTTPS、前端静态资源）。
3. **AI Service / Crawler Service 为独立 Python 进程**：因技术栈异构而独立，不复制业务代码。
4. **RabbitMQ 只解耦两个异步场景**：AI 任务队列、爬虫采集队列。业务 CRUD 保持同步 HTTP → DB。
5. **明确否决**：自研 RPC、服务注册中心、微服务拆分、跨服务直连数据库。

## Rationale

1. **业务内聚，部署简单**：核心 CRUD 在同进程完成，事务与一致性由 MySQL 保证，3-6 个月可交付
2. **MQ 用于“真正慢的边界”**：LLM 调用与网页抓取是需要重试、削峰、解耦的异步负载，MQ 在这里才物有所值
3. **异构即独立**：AI/爬虫与 C++ 业务不存在复用代码的可能，独立进程不产生维护负担
4. **否决微服务的理由要能讲清**：面试答“为什么不做微服务”＝“规模未到、单人交付约束、避免分布式一致性复杂度”，这是高级工程师的取舍，不是能力不足

## Consequences

### Positive

- 开发路径清晰，可迭代交付（先单体跑通，再加 AI/爬虫）
- 面试可讲三层取舍：进程内模块 / MQ 解耦边界 / 异构服务独立
- 部署 = docker-compose 一套，可演示

### Negative

- 业务模块无法独立扩缩容（当前不需要）
- 引入 RabbitMQ 需要学习与运维成本

### Risks

- 模块边界模糊导致退化回“大泥球” → 缓解：06 编码规范强制 Controller/Service/DAO 分层，禁止跨模块引用实现
- 未来业务膨胀需要拆分 → 缓解：模块之间天然可沿 bounded context（用户/简历/岗位/投递）切成进程，本 ADR 的模块划分即预留了该边界
